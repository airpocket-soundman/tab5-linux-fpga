# 外部RAM活用の基板なし開発

更新日：2026-10-23。作業開始HEAD：`f37b830d878b8e52b4e06f983f38ef1c828f5061`。

## 目的と実装範囲

主目的であるFPGA DDR3活用に向け、アプリが明示的に確保・保存・復元・分割処理する場合の寿命と境界条件をPC上で検証する。実装は `tools/fpga-memory/`。Python標準ライブラリだけで実行するホスト用の参照モデルであり、LinuxドライバでもMeOS移植でもない。

128MiBをデフォルト容量とする一時ファイルを模擬外部記憶として用いる。128MiBは容量モデルのパラメータであり、DDR3全域を実機でアクセスできたという意味ではない。転送ごとの最大長を既定4096バイトに制限し、容量相当のbytearrayをPC上に確保しない。ファイルシステムのキャッシュやPython実行時のメモリまで4096バイト以下とする主張ではない。

通常RAMの増設、透明なページング、Linux swap、無改造アプリのmalloc拡大は実装しない。物理通信、RTL、PARLIO、DMA、IRQ、帯域・遅延・CPU負荷は未検証。ファイルI/Oの実行時間をFPGA性能の見積もりには使わない。

## モデル上の操作と制約

| 操作 | 挙動 |
| --- | --- |
| allocate(size) | 正のサイズをfirst fitで割り当て、公開前に全範囲をゼロ初期化。連続空き領域が足りなければ失敗 |
| free(handle) | ハンドルを無効化し、隣接する空き領域を結合。再確保時には前の内容を読めない |
| read / write | オブジェクト内のoffsetと長さを検査。1回の要求がtransfer_limitを超えれば拒否 |
| tiles | 指定範囲を小さなブロックで順次読み出す。末尾の短いブロックも返す |
| copy | 小さなread/writeの反復。単一オブジェクト内の重複範囲もmemmoveと同じ結果にする |
| close | 一時ファイルを閉じ、そのセッションの全ハンドルを無効化 |

ハンドルはインスタンス内のPythonオブジェクトの同一性で管理する。番号・サイズを同じにした偽物、別インスタンス、解放済み、close以前のハンドルは拒否する。番号を通信へ載せる仕様ではない。実ドライバにはsession ID・generation等による寿命管理が別途必要となる。

範囲検査は `offset <= size` と `length <= size - offset` を用いる。負値、bool、非整数、容量外、転送上限超過を拒否する。範囲末尾の長さ0は許可し、長さ0のallocateは拒否する。整数オーバーフローのないPythonモデルであり、将来Cへ実装するときには整数幅も明示して検証する。

並行利用・永続化・自動再試行・トランザクションは提供しない。複数ブロックのcopy途中で例外が発生すると転送済みの範囲は変更される。エラーを隠して成功扱いにはしない。特に重複copyを失敗後に単純再試行すると元データがすでに変わっている可能性があり、回復処理の別設計が必要。allocateの初期化失敗時はハンドルと割り当て情報を公開せず、次のallocateで再初期化する。

既存の接続試験v0は固定8バイトのID/echo/反転用であり、このモデルの操作とは接続していない。メモリwire ABI、opcode、CRC、要求ID、timeout値を確定したものとして扱わない。

## 実行と確認結果

Windows PowerShell、CPython 3.12.7で実行。実機は使用せず、ネットワーク・シリアル・GPIO・フラッシュ操作なし。

```text
python -m unittest discover -s tools/fpga-memory -p test_memory_mock.py -v
python tools/fpga-memory/memory_mock.py --mock
```

12テスト成功。分割保存・復元、負値・巨大offset・転送上限、偽造/別セッション/解放済みハンドル、全容量確保・解放領域結合・再使用時ゼロ初期化を確認した。重複copyは固定seedの150ケースをPythonのスライス代入と照合。途中書き込みのtimeout注入では例外の伝播、部分更新、自動再試行なしを確認し、別オブジェクトへの明示的な再転送で復元できることを確認した。初期化失敗時の割り当て不成立も確認した。一時ファイルの短いread/writeも注入し、OSErrorと部分更新を確認した。転送回数・バイト数カウンターは成功を確認できた要求だけを計上し、失敗要求の副作用量を表さない。

CLIは1,048,593バイトを生成して分割保存し、別オブジェクトに復元して、SHA-256と各バイトの合計を分割処理する。確認結果：

| 項目 | 結果 |
| --- | --- |
| backend | host-file-mock |
| physical_link_tested | false |
| 最大転送要求 | 4096バイト |
| read回数・合計 | 514回・2,097,186バイト |
| write回数・合計 | 1028回・4,194,372バイト（2領域のゼロ初期化を含む） |
| 復元後のバイト合計 | 131,067,070 |
| SHA-256 | `f4bf9b8dec6e3e28b2ec33266145d244fe97a6bce1ec054ace053bab67d2ef9a` |

CLIは`--mock`必須。データは一時ファイルに保存し、終了時に閉じる。実アプリのデータを入力する機能はない。

### 容量を変えた分割処理

`--size`は1オブジェクトのサイズ（1〜134217728バイト、上限128MiB）、`--transfer-limit`は1回の転送長上限（1〜1048576バイト、上限1MiB）。一時ファイルの容量はsizeの2倍で、元データと復元先を保持する。最終的なファイル容量の上限は256MiB。書き込み合計量はゼロ初期化も含めsizeの4倍となる。データ生成は全体を保持せず、`index % 251`のパターンを転送単位で生成する。生成時に数個の転送単位相当のPython一時データを使用するため、転送長上限をプロセスのRAM使用量上限とは扱わない。

JSONの`readback_crc32`は復元先を順次読み出して計算するCRC-32（Python zlib、初期値0、8桁小文字hex）。既定サイズでは`a28d8150`。SHA-256照合と併せて、Linux/MeOSのホスト参照実装を同じパターンで比較するために使う。wire上のCRC仕様を定めたものではない。

```text
python tools/fpga-memory/memory_mock.py --mock --size 67108864 --transfer-limit 65536
```

64MiBオブジェクト、転送上限64KiBで実行した結果：

| 項目 | 結果 |
| --- | --- |
| bytes_verified | 67,108,864 |
| 最大転送要求 | 65,536バイト |
| 一時ファイル容量 | 134,217,728バイト |
| read回数・合計 | 2048回・134,217,728バイト |
| write回数・合計 | 4096回・268,435,456バイト |
| 復元後のバイト合計 | 8,388,607,751 |
| readback_crc32 | `8d536c88` |
| SHA-256 | `98dc891b284e4d84ac25b0c0a24fdbe39a7f0dbd643ad5e8aa06e02fc6258254` |

追加の故障テストでは、重複copyが一部成功してから失敗した場合、元データがすでに変更され、全体を無条件に再試行しても正しい結果に戻らない例を確認した。これは自動再試行を提供しない理由の確認であり、原子的copyや回復機能の実装ではない。実機性能・プロセスRAM最大値の測定は行っていない。

## 残課題と次の作業

1. 研究リポジトリ側で用途別評価へ接続する。まず実データを分割できるアプリを選び、作業領域・転送量・参照頻度を記録する。
2. メモリAPIの提案書でアドレス幅・最大長・要求ID・CRC・エラー・重複要求・resetとセッション寿命を定義する。現v0とは別にレビューする。
3. Cで固定バッファのAPIを実装する際、本モデルの境界条件と照合する。実機用ハンドルをPythonの同一性モデルのまま移植しない。
4. 実基板とTab5が使える段階で低速接続試験、DDR3の領域別パターン照合、全域分割アクセス、失敗復帰を検証する。その後に帯域・遅延・CPU負荷とアプリ効果を測定する。

この作業によってL2〜L4を完了としない。RAM活用アプリの制御ロジックの準備とPC上の確認を進めた段階である。
